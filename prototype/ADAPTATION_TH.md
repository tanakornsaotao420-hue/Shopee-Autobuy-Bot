# Campaign Planner 0.2: การนำ Workflow มาปรับใช้

ต้นแบบนี้ทำงานแยกจากโปรแกรม C# เดิม รัน `START_WINDOWS.bat` ในโฟลเดอร์นี้
ต้องมี Python 3 พร้อม Tkinter ไม่ต้องติดตั้ง Selenium และไม่ใช้บัญชี Shopee
สถานการณ์ทั้งหมดเป็น fixture ในหน่วยความจำ ไม่ได้อ่านหน้าเว็บหรือ DOM จริง

## สิ่งที่เพิ่มจาก 0.1
- ตรวจ snapshot สุดท้าย: สินค้า/รุ่น/จำนวนต้องตรงเพียงรายการเดียว ที่อยู่ตรง บัตรตรงและถูกเลือกจริง
- หากไม่พบบัตรหรือพบหลายใบให้หยุด แม้เลขท้ายบัตรอาจเหมือนกัน
- ตรวจ THB และจำนวนเงินเป็นสตางค์ คิดเพดานจากยอดสุดท้าย ไม่ใช่ราคาที่หน้าสินค้า
- ตรวจคูปองบังคับและอายุข้อมูลไม่เกิน 10 วินาที (ค่าตั้งต้นของต้นแบบ)
- หน้า payment อย่างเดียวให้ UNKNOWN ไม่ถือว่าชำระสำเร็จ
- จำลองผิดบัตร หลายบัตร ผิดรุ่น สินค้าเกิน และข้อมูลเก่า

## การออกแบบที่ปรับจาก source เดิม
ศึกษา master commit a682ee974a82cfedb0a2201dc8aa8b2a96b5e072
ใช้แนวคิด Profile / Schedule / Checkout / Payment แยกหน้าที่ใหม่
ไม่ได้คัดลอกตัวคลิก Selenium, PIN, credential หรือ selector มาใช้
ใช้ SQLite transaction กันงบและส่ง intent จำลองเพียงครั้งเดียว
การสร้างงานใหม่ด้วยปุ่มบันทึกยังถือเป็นคนละเจตนาซื้อ แม้สินค้าเหมือนกัน
งาน UNKNOWN ไม่ถูก retry อัตโนมัติ และยังกันงบจนกำหนดผลของคำสั่งเดิม

## โครงสร้าง
- app.py: หน้าต่างภาษาไทยและตัวตั้งเวลาทุก 1 วินาที
- engine.py: สถานะงาน งบแคมเปญ และประวัติใน SQLite
- checkout_guard.py: validation ที่ไม่พึ่งหน้าจอ พร้อม fixture adapter
- test_engine.py / test_checkout_guard.py: unit และ integration tests แบบ offline

## วิธีลองกรณีที่เคยเสี่ยง
1. เปิดโปรแกรม ตั้งเวลาอีก 1 นาที เลือก wrong_card แล้วบันทึก
2. เมื่อถึงเวลา งานต้อง STOPPED และไม่มีเลขคำสั่งซื้อจำลอง
3. สร้างงานใหม่เลือก payment_page_only เมื่อถึงเวลาจะ UNKNOWN และกันงบไว้
4. ปิดแล้วเปิดใหม่ งานเดิมต้องไม่ถูกส่งซ้ำ
5. เลือกงาน UNKNOWN แล้วจำลองผลสำเร็จหรือล้มเหลวของคำสั่งเดิม

## ขอบเขตที่ยังไม่ได้ทำ
ยังไม่แก้หรือเชื่อม runtime C# เดิม และไม่ได้ยืนยันว่า build โปรแกรมเดิมผ่าน
ไม่มีหน้าเว็บจำลองแบบ HTML และไม่มี browser integration test ในรุ่นนี้
ไม่มีตัวเชื่อมซื้อจริง ไม่มี OTP automation ไม่มีการชำระเงิน
ไม่ใช่ patch ที่ทำให้โปรแกรม C# เดิมปลอดภัยขึ้น ผู้ใช้ต้องเปิดโปรแกรมใน prototype เท่านั้น
ห้ามตีความ PAID_SIMULATED ว่าเป็นธุรกรรมจริง

## งานก่อนใช้เงินจริง
1. ยืนยันช่องทางที่แพลตฟอร์มอนุญาต และตรวจเงื่อนไขโปรบนช่องทางนั้น
2. เลือกว่าจะย้าย controller ไป C# หรือเชื่อมผ่าน IPC ที่มี schema ชัดเจน
3. ให้ adapter อ่าน snapshot จริงและตรวจ fresh quote ก่อน submit
4. บันทึก intent ลงฐานข้อมูลให้ durable ก่อน network call แล้ว reconcile ด้วย order id
5. ทดสอบ crash หลัง submit, timeout, restart และ concurrency กับ payment sandbox
6. ยืนยันผลจากสถานะคำสั่งซื้อและชำระ ไม่ใช่ URL หรือข้อความแจ้งเตือนอย่างเดียว
7. แยก NEEDS_USER สำหรับ OTP/CAPTCHA และให้เจ้าของบัญชีดำเนินการ

SQLite transaction ของ simulator ไม่ใช่การรับประกัน exactly-once สำหรับผู้ให้บริการภายนอก
ระบบจริงต้องมี idempotency ที่ provider รองรับหรือ reconciliation ที่พิสูจน์ผลได้
